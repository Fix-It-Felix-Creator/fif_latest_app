# Admin Panel — Notifications

End-to-end reference for building a web admin panel that sends in-app
**and native push** notifications to Fix It Felix Pro users.

**Status**: live on `fifcloud` (europe-west1). FCM wired end-to-end —
verified iOS delivery on 2026-04-20.

Companion doc: `docs/push-notifications-setup.md` (APNs / Xcode / Android
native setup — one-time per platform).

---

## 1. Data model

Notifications live in Firebase Realtime Database under:

```
/notifications/{uid}/{notificationId}
  title:      string     (required — 1..80 chars recommended)
  body:       string     (required — any length; 140+ opens detail view)
  type:       string     (see §4 catalogue, default "system")
  payload:    object|null (free-form — see §5)
  createdAt:  number     (ms since epoch, server-generated)
  read:       boolean    (false on create)
  readAt:     number|null (ms since epoch, set on mark-read)
```

- `{uid}` = Firebase Auth UID of the recipient.
- `{notificationId}` = an RTDB push key generated by the backend.
- A fan-out (many recipients) is one multi-path `update()` — atomic on the
  server. No partial-delivery state.

## 2. RTDB security rules

```json
"notifications": {
  "$uid": {
    ".read":  "auth.uid === $uid",
    ".write": false
  }
}
```

- Users can **read** only their own notifications (real-time).
- Users can **never write** directly — all writes go through the Admin SDK
  (Cloud Functions).

## 3. Admin identity

An admin is a Firebase user whose UID appears under:

```
/config/admin/systemRoles/{uid}
  role:     "admin" | "superAdmin"
  isActive: true
```

Backend middleware (`functions/src/lib/admin.ts`):

```ts
export async function isAdmin(uid: string): Promise<boolean> { … }
export async function requireAdmin(req, res, next): Promise<void> { … }
```

Any admin-only endpoint chains `verifyFirebaseToken → requireAdmin`.
Non-admin callers get `403 { success: false, message: "Admin access required" }`.

## 4. `type` catalogue

`type` is a free-form string. The mobile app uses `String.contains(...)` to
pick an icon — exact match not required, but using these preset strings keeps
behaviour predictable. The **Icon** column is the Lucide icon shown on the
list row.

| Category       | Suggested `type` strings                        | Icon              |
| -------------- | ----------------------------------------------- | ----------------- |
| Announcement   | `announcement`, `promo`                         | `megaphone`       |
| Payment / sub  | `payment_success`, `payment_failed`, `subscription_renewal`, `subscription_update`, `subscription_expiring` | `creditCard` |
| Jobs           | `job_offer`, `job_accepted`, `job_completed`, `job_update`, `job_declined` | `briefcase` |
| Messages       | `new_message`, `chat`                           | `messageSquare`   |
| Staff / team   | `staff_invitation`, `staff_assignment`, `team_update` | `users`     |
| Verification   | `verified`, `welcome`, `milestone`              | `circleCheck`     |
| Info / updates | `tip`, `policy_update`, `release_notes`         | `info`            |
| Fallback       | `system`, anything else                         | `bell`            |

> The matcher is `type.toLowerCase().contains("payment")` etc. — so
> `payment_success`, `payment-failed`, `PaymentReminder` all hit the same
> category. Pick consistent snake_case to keep the data readable.

## 5. `payload` schema

Free-form `Record<string, unknown>` passed through to the mobile app.

Recognised optional keys (today):

| Key                                  | Purpose                                               |
| ------------------------------------ | ----------------------------------------------------- |
| `imageUrl` / `image_url` / `image`   | Full-width image on the detail screen                 |
| `route` (planned)                    | Deep-link target, e.g. `"/subscription"`              |
| `routeArgs` (planned)                | Map passed as route `arguments`                       |

Anything else is preserved verbatim but unused — safe for forward-compat.

### 5.1 Image sizing guidelines

The detail screen renders `payload.imageUrl` inside a `ClipRRect` with
`BoxFit.cover` across the full content width (screen − 32 px padding).
Placeholder height while loading is 200 dp.

| Property         | Recommendation                          | Notes                                    |
| ---------------- | --------------------------------------- | ---------------------------------------- |
| **Aspect ratio** | **16:9** (preferred), or 2:1 / 3:2      | Avoid square or portrait — `BoxFit.cover` will center-crop. |
| **Resolution**   | **1200 × 675 px** (16:9)                | Covers 3x-density phones (iPhone Pro, Pixel Pro). 800 × 450 px is acceptable for smaller devices. |
| **Minimum**      | 800 × 450 px                            | Below this, 3x screens will visibly upscale. |
| **Maximum**      | 1920 × 1080 px                          | Anything larger wastes bandwidth — scaling is handled client-side. |
| **File size**    | ≤ 300 KB ideal, ≤ 800 KB hard cap       | Directly affects first-load time; subsequent loads hit the disk cache. |
| **Format**       | **WebP** (best), JPEG (photos), PNG (graphics with transparency) | Avoid TIFF / BMP — unsupported by the CDN path. |
| **Colour space** | sRGB                                    | Wide-gamut (Display P3) renders washed-out on Android. |
| **Host**         | HTTPS, publicly readable, no auth       | No bearer headers supported — pre-sign if you use private storage. |

**Compression tips**:
- JPEG quality 80–85 gives a solid size-to-visual tradeoff.
- If using Firebase Storage, prefix uploads with `notifications/` and serve
  the public download URL (or a CDN-fronted equivalent).
- Strip EXIF metadata to shave an extra 5–20 KB.

**Behaviour edge cases**:
- Broken URL → shown as a grey panel with a "no-image" icon (handled by
  `errorWidget`). The rest of the notification still renders.
- Very tall images (portrait) → cropped vertically by `BoxFit.cover`; the
  important subject should sit in the horizontal middle third.
- First load: spinner placeholder. Re-open: instant (disk cache).

## 6. Detail-view trigger

When the user taps a row, the mobile app opens the **detail screen** if
**either** is true:

- `body.length > 140`, or
- `payload.imageUrl` (or `image_url` / `image`) is a non-empty string.

Short, image-less notifications just mark-read inline.

Images are rendered with `cached_network_image` — the first load caches to
disk, subsequent loads are instant and offline-available. URLs must be
HTTPS + publicly readable (no auth headers).

## 7. Backend endpoints

All endpoints mount on the `/api` Cloud Function (region
`europe-west1`, project `fifcloud`) and require
`Authorization: Bearer <firebaseIdToken>`.

Base URL: `https://europe-west1-fifcloud.cloudfunctions.net/api`
(or the Cloud Run URL exposed by the deploy — both work).

### 7.1 `POST /notifications/send` — admin only

Fan-out to specific UIDs or every user. Sends **both** the in-app RTDB
record **and** a native FCM push in one call.

```jsonc
{
  "title":     "Spring release preview",          // required
  "body":      "Long-form announcement text…",    // required
  "type":      "announcement",                    // optional, default "system"
  "payload":   { "imageUrl": "https://…/a.jpg" }, // optional
  "toUserIds": ["uid1", "uid2"],                  // recipients set A
  "toAll":     false                              // OR set B — scans /users
}
```

- Either `toAll: true` **or** a non-empty `toUserIds` array is required.
- Response:
  ```json
  {
    "success": true,
    "sent": 42,          // in-app records written
    "pushSent": 38,      // successful FCM deliveries
    "pushFailed": 4      // failed (stale tokens are auto-deleted)
  }
  ```

### 7.2 `POST /notifications/mark-read` — authenticated user

```jsonc
{ "notificationId": "…" }  // mark one
{ "all": true }            // mark every unread for the caller
```

Response: `{ "success": true }` (for one) or `{ "success": true, "updated": <n> }` (for all).

### 7.3 `POST /notifications/clear` — authenticated user

```jsonc
{ "notificationId": "…" }  // delete one
{}                         // delete everything for the caller
```

Response: `{ "success": true }`.

## 8. Calling `/notifications/send` from a web admin panel

```ts
import { getAuth } from "firebase/auth";

const BASE = "https://europe-west1-fifcloud.cloudfunctions.net/api";

export async function sendNotification(body: SendBody) {
  const user = getAuth().currentUser;
  if (!user) throw new Error("Not signed in");
  const token = await user.getIdToken();

  const res = await fetch(`${BASE}/notifications/send`, {
    method: "POST",
    headers: {
      "Authorization": `Bearer ${token}`,
      "Content-Type": "application/json",
    },
    body: JSON.stringify(body),
  });
  if (!res.ok) throw new Error(await res.text());
  return res.json();
}

interface SendBody {
  title: string;
  body: string;
  type?: string;
  payload?: Record<string, unknown>;
  toUserIds?: string[];
  toAll?: boolean;
}
```

## 9. Recommended admin panel UX

### 9.1 Compose / Broadcast page

- **Recipients** — radio: `All users` or `Specific users` (multi-select
  autocompleter fed from `/users` shallow list).
- **Type** — dropdown seeded from §4 catalogue + a "custom string" option.
- **Title** — single-line (hard-cap 80 chars).
- **Body** — multi-line textarea, no server cap. Live-preview two-line
  truncation so the author sees how it renders on the list.
- **Image URL** — optional URL field. Validate with a HEAD request and show a
  preview. Populates `payload.imageUrl`.
- **Deep-link (future)** — route selector.
- **Send** — POST to `/notifications/send`, spinner, toast the `sent` count.

### 9.2 Preview

Render the payload as it will appear in the mobile list AND detail view
side-by-side. Catches long-body and broken-image mistakes before send.

### 9.3 Audit log (optional, not yet built)

If you want send-history, write one row inside `sendNotification`:

```
/notifications_admin_log/{pushKey}: {
  adminUid, adminEmail, createdAt, recipientCount, title, type
}
```

Then list it on an /admin/history page.

## 10. Mobile-app integration (reference — already wired)

- `lib/models/in_app_notification.dart` — RTDB-shaped model.
- `lib/repositories/notifications/notifications_repository.dart` — real-time
  stream (`watchAll()`) + REST mutations (mark-read / clear).
- `lib/blocs/notifications/` — `NotificationsBloc` + event + state.
  Exposes `state.unreadCount`.
- `lib/widgets/notification_badge.dart` — wraps any widget with a red
  counter; subscribes to the bloc by default.
- `lib/screens/notifications/notifications_screen.dart` — list view with
  `Today` / `Yesterday` / full-date section headers, pull-to-refresh,
  swipe-to-clear, popup menu (mark all, clear all), category icons.
- `lib/screens/notifications/notification_detail_screen.dart` — full
  body + cached image.
- `screens/tradesman/home/home_page.dart` — bell AppBar button wrapped in
  `NotificationBadge`, routes to `/notifications`.

## 11. Operational checklist

1. Seed admin (once per admin user):
   ```
   /config/admin/systemRoles/<adminUid>
     role: "admin"
     isActive: true
   ```
2. Deploy the backend (if changes made):
   ```bash
   cd functions && npm run build && firebase deploy --only functions:api --project fifcloud
   ```
3. Call `/notifications/send` — the mobile app's bell badge + list update
   live via RTDB `onValue`. If an FCM token is stored for the recipient,
   a native banner also appears (iOS requires APNs upload — see
   `push-notifications-setup.md`).
4. Tail logs: `firebase functions:log --only api --project fifcloud`.

## 12. Sending a notification directly via Firebase CLI (dev shortcut)

For local testing you can bypass the endpoint and write to RTDB as admin:

```bash
NOW=$(python3 -c 'import time; print(int(time.time()*1000))')
firebase database:update "/notifications/<UID>" --project fifcloud --force \
  --data '{"manual_'"$NOW"'":{"title":"Hello","body":"Direct write","type":"system","createdAt":'"$NOW"',"read":false,"readAt":null,"payload":null}}'
```

This still fires the `onValue` stream on the device exactly the same way.

## 13. Native push notifications (FCM)

`POST /notifications/send` now does two things:
1. Writes the in-app record under `/notifications/{uid}/{id}`
2. Looks up each recipient's FCM tokens under `/users/{uid}/fcmTokens/`
   and delivers a native OS push via `getMessaging().sendEach()` in
   batches of 500.

No extra admin-panel action is required — calling the same endpoint with
the same body triggers both in-app and native delivery. Response now
includes `pushSent` and `pushFailed` counts.

**Token storage**:
```
/users/{uid}/fcmTokens/{safeTokenKey}: {
  token: string,
  platform: "ios" | "android",
  createdAt: number,
  lastSeenAt: number
}
```

**Stale tokens** returning `messaging/registration-token-not-registered`
or `messaging/invalid-registration-token` are auto-deleted from RTDB on
the next send.

**Platform setup** (APNs upload, Xcode capabilities, Android channel)
is documented in `docs/push-notifications-setup.md` — complete that
before the first send.

## 14. Future enhancements

- **Topic-based broadcast**: subscribe every device to a `broadcast` FCM
  topic on sign-in. One `messaging().send({ topic: "broadcast", ... })`
  reaches all devices — no per-token iteration. Required for 10k+ users.
- **Per-notification TTL**: `expiresAt` field + scheduled cleanup.
- **Category filters** on the mobile list (group by `type`).
- **User preferences**: opt-in/opt-out per notification category.
- **Audit log** (see §9.3).
- **Rich content**: markdown-rendered body, multiple images, CTAs.
