# fif_pro

## Admin panel — extend it alongside the apps

`fif-admin/` (Next.js on Vercel) is the staff panel over **both** apps. They
share one Supabase project; `profiles.account_type` is the only thing separating
them — `tradesman`/`business` are the Pro app, `customer` is the customer app.

**When a change to `fixitfelixpro/` or `fixitfelix/` gives staff something new to
see or decide, add it to the panel in the same piece of work.** The panel is what
a support ticket is answered from: a field that exists in the app and nowhere
here is a question nobody can answer.

| Change in either app | Do this in `fif-admin/` |
|---|---|
| New per-user table (keyed `owner_id`) | Add it to `OWNER_TABLES` in `lib/queries.ts`, then a tab on the relevant detail page |
| New `profiles` column | A `KV` row on whichever detail page it applies to — tradesperson, customer, or both |
| New value in a status CHECK constraint | Map it in `statusTone()` (`components/ui/badge.tsx`). Unmapped values render neutral, never wrong |
| New cross-user table worth a ledger | A page under `app/(panel)/`, listed in `lib/nav.ts` with the permission that reveals it |
| New server-owned column (one `profiles_guard_server_columns` reserves) | A server action in `app/(panel)/_actions/`, a permission in `lib/roles.ts`, a `recordAdminAction()` call |
| New moderation or support decision | Same as above. Never expose a write without the permission check *inside* the action |
| New `app_config` key | Nothing — `/config` renders whatever keys exist |
| New notification type | Nothing — the compose screen reads types from the data |

Three things that are easy to get wrong:

- **Customers and tradespeople are separate pages on purpose.** A customer has no
  trade, no verification file, no subscription and no ledger. Do not merge them
  into one filtered list; the customer rows would be three-quarters dashes.
- **Every write needs all three of**: a permission resolved from the caller's own
  session *inside* the server action (a hidden button is not a check), an audit
  row, and a `revalidatePath`.
- **Roles live in `lib/roles.ts`, not the database** — the DB stores only the role
  name. But the `api` edge function keeps its own narrower list (`SENDING_ROLES`
  in `functions/api/lib/context.ts`) for notification sends; widening one without
  the other produces a 403 from a button that rendered.

One deployment per environment, by design: staging and production are separate
Supabase projects and get separate Vercel projects, so neither holds a credential
that reaches the other's database.
